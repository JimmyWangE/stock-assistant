# 架构方案

更新日期：2026-11-16

## 技术选型

选型标准：好维护、资料多、有同类案例。

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | AkShare 是 Python 库；原生支持异步和流式输出；TradingAgents-CN、daily_stock_analysis 同栈 |
| 前端 | Vue 3 + TypeScript | 国内资料最多；TradingAgents-CN 同栈 |
| 图表 | ECharts | 一个库覆盖 K 线和财务图表，中文文档全 |
| 数据库 | PostgreSQL | 用户和会话是关系型数据；自带全文搜索 |
| 缓存与排队 | Redis | 行情缓存、模型并发排队 |
| PDF 导出 | 服务端无头浏览器渲染 | 图表和表格原样进入 PDF |
| 部署 | systemd + Nginx，不使用 Docker | 服务器上已有 PostgreSQL、Redis、Nginx 程序，直接启动项目专用实例 |

## 组成

```
浏览器（Vue 3 + ECharts）
   │  HTTPS；回答走流式连接
Nginx
   │
FastAPI 后端
   ├─ 账号：注册、登录、鉴权
   ├─ 对话：接收问题 → 排队 → 调模型 → 执行工具 → 流式返回
   ├─ 工具：行情、K 线、财报、选股、新闻（封装 AkShare）
   ├─ 会话：保存、搜索、重命名、删除、到期清理
   └─ 导出：会话 → PDF
   │
   ├─ PostgreSQL（用户、会话、消息）
   ├─ Redis（行情缓存、排队计数）
   ├─ 自研模型 API（外部）
   └─ AkShare → 公开数据网站（外部）
```

## 一次提问的流程

1. 前端发送问题，后端立即回一条状态消息（"已收到"或"排队中，前面 N 人"）。
2. 后端在并发名额内调用模型 API，带上工具定义和会话上文。
3. 模型请求调用工具时，后端执行对应的 AkShare 封装，前端显示"正在查询行情"等状态。
4. 工具结果返回模型，模型流式输出正文；图表和表格以结构化数据块随流下发，前端用 ECharts 渲染。
5. 回答结束后，问题、回答、图表数据、来源链接一并写入数据库。

## 关键设计与对应的验收项

| 设计 | 说明 | 对应验收 |
|---|---|---|
| 收到即回状态 | 不等模型，后端先推一条状态消息 | B1 |
| 并发闸门 | Redis 计数，同时最多 200 个模型请求，超出排队并推送排队位置 | B10 |
| 行情短缓存 | 同一只股票的行情缓存数秒，避免 300 人重复抓取被上游限流；缓存时长须小于 5 秒 | B3、B11 |
| 选股走本地库 | 定时把全市场行情和财务指标落到 PostgreSQL，选股条件转成查询，不临时抓全市场 | B7 |
| 工具失败不中断 | 工具出错时把"未获取"作为结果交还模型，由模型标注后继续作答 | B9 |
| 图表存数据不存图 | 消息里保存图表的原始数据，重开会话和导出 PDF 时重新渲染，即生成时的快照 | B4、C1、C5 |
| 按用户过滤 | 所有会话查询都带当前用户条件，在数据访问层统一加 | A3 |
| 到期清理 | 最后对话时间超过 30 天（`CONVERSATION_KEEP_DAYS`）的会话：查询时一律当作不存在，后台每小时实际删除一次。重命名不改最后对话时间 | C6 |
| 历史搜索 | 数据库 `ILIKE` 匹配标题和消息正文，不区分大小写；`%`、`_` 按字面匹配。数据量小，暂不建全文索引 | C2 |
| 删除会话 | 先删消息再删会话，不依赖数据库级联；回答生成中被删除的会话不再保存回答 | C4 |

## 数据工具（已实现部分）

模型通过工具调用取数，一次回答最多调用 4 轮工具。工具返回两样东西：给模型读的精简文字摘要，和直接交给页面展示的图表数据（不经过模型，不占上下文）。

| 工具 | 作用 | 数据来源 | 缓存 |
|---|---|---|---|
| `get_stock_quote` | 最新价、涨跌幅、今开、最高、最低、昨收、成交量、成交额 | 腾讯财经实时报价；不可用时换新浪财经实时报价；都不可用时退到新浪 1 分钟线 | 1 秒 |
| `get_kline` | 1/5/15/30/60 分钟、日、周、月 K 线，页面画图，模型拿摘要 | 新浪财经（经 AkShare） | 分钟线 20 秒，日线以上 5 分钟 |

| `get_financials` | 最近 2–8 个报告期的主要财务指标，页面显示表格，模型做解读 | 新浪财经财务摘要（经 AkShare） | 1 小时 |
| `get_stock_news` | 一只股票最近的新闻，含原文链接 | 东方财富个股新闻（经 AkShare） | 2 分钟 |
| `get_market_news` | 财经媒体的最新市场资讯，可按关键词筛选，含原文链接 | 东方财富财经资讯，最近 200 条（经 AkShare） | 1 分钟 |
| `get_market_overview` | 大盘概况：主要指数、涨跌家数与分布、三市成交额、成交额前五、行业领涨领跌与资金流向 | 市场概览的快照（见下） | 随快照 |
| `get_policy` | 官方最新发布的政策文件和通告：标题、日期、官网原文链接，可按机构和标题关键词筛选 | 国务院、证监会、中国人民银行、财政部、国家发展改革委官网的发布列表（直接抓取） | 10 分钟 |

- 股票可用 6 位代码或简称指定。名称表随代码发布一份快照（`backend/app/tools/data/stocks.csv`），后端在后台每 12 小时从交易所刷新；刷新失败就继续用现有的，不影响查询。
- 没有使用东方财富的行情接口：实测其服务器对请求限流，首次请求即被拒绝，不适合 300 人使用。
- 实时报价直接请求腾讯、新浪的公开报价接口（AkShare 没有封装单只股票的实时报价，这是用户同意的例外）。实测腾讯报价滞后 1–5 秒，对应验收 B3。
- 日线以上用前复权数据；分钟线用不复权数据，因为复权后的分钟线不含当天。
- 缓存目前在后端进程内存里，没有用 Redis（后端是单进程）。
- 每个工具在结果末尾给出写好的来源链接，要求模型原样引用；模型采样温度设为 0.3 以减少漏调工具和改写数据。
- 官方政策原文直接抓取五家官网的发布列表（AkShare 没有对应接口，这是用户要求的）。每家一个解析函数，写在 `backend/app/tools/policy.py` 的 `SOURCES` 里；某一家改版或不可达时只影响那一家，并在回答里如实说明。只取标题、日期和链接，不取正文，模型不得臆测条款内容。要增加机构，在 `SOURCES` 里加一行。
- 登录后的首页是"市场概览"，对话在"智能投研"（`/chat`、`/c/<会话 id>`）。概览页和对话页右侧的看板共用一份市场快照 `GET /api/market/board`，不经过模型。后台任务定时刷新这份全站共用的快照，接口直接返回：页面从不等待上游，对每个上游的请求频率固定，与在线人数无关；两分钟没人看页面就停止刷新。各板块独立，某个数据源取不到时那一块不显示。
  - 9 个指数（上证、深证、创业板、沪深 300、科创 50、上证 50、中证 500、中证 1000、北证 50）与当天分时：腾讯财经，5 秒 / 60 秒。
  - 全市场统计（涨跌家数、涨停跌停、涨跌分布、涨幅榜、跌幅榜、成交额榜、三市成交额）：腾讯报价对沪深京全部股票逐只统计，约 19 次批量请求、不到 1 秒，30 秒一次；涨跌家数在腾讯不可用时退到乐咕乐股。
  - 行业板块（约 90 个行业的涨跌幅、资金净流入、领涨股，用于热力图和资金流向）：同花顺（经 AkShare），2 分钟。
  - 财经快讯：东方财富（经 AkShare），1 分钟；官方政策复用 `get_policy` 的数据，10 分钟。
  - 代码在 `backend/app/overview.py`。
- 指数详情 `GET /api/market/index/<代码>`：当日分时和最近 120 个交易日日 K（腾讯财经），同一指数 15 秒内只取一次。腾讯没有北证 50 的历史日线，该指数只显示分时。
- 登录页的指数行情 `GET /api/market/ticker` 不需要登录，只返回 5 个指数的公开点位。
- 模型工具 `get_market_overview` 把同一份快照整理成文字，供市场复盘和指数解读使用；没人看页面、快照已停时会先现取一次。
- 行情查询除文字外还返回一张行情卡片（`quote` 类型的展示块），价格数字由页面直接展示，不经模型转述。

## 数据库迁移

表结构变更用 Alembic 管理，迁移文件在 `backend/migrations/versions/`，后端启动时自动执行到最新。改动 `app/models.py` 里的表结构后必须新增一个迁移文件。

## 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| AkShare 抓取公开网站，无服务保障，上游改版或限流会失效 | B3–B8 | 短缓存降低请求量；工具失败按 B9 处理；工具层做成可替换，日后可换商业数据源 |
| 5 秒延迟在上游变慢时可能超标 | B3 | 回答中始终标注数据时间；上线前在交易时段实测 |
| 无头浏览器渲染 PDF 占资源 | C5 | 导出任务单独限并发 |
| 注册不设限，网址外泄后外部人员可使用 | 整体 | 首版已确认不处理；可通过只在内网开放来规避 |

## 模型服务与服务器

| 项 | 内容 |
|---|---|
| 协议 | OpenAI 兼容 HTTP API |
| 地址 | 内网地址，不写入仓库，部署时在 `.env` 的 `LLM_BASE_URL` 中填写；对话接口为 `/v1/chat/completions` |
| 密钥 | 存于服务器上的文件，路径不写入仓库，部署时在 `.env` 的 `LLM_API_KEY_FILE` 中填写；后端进程的专用账户对该文件只有读权限 |
| 工具调用 | 请求中用 `tools` 声明，可设 `"tool_choice": "auto"` |
| 服务器 | Linux，可访问外网 |

实测到的模型行为（模型名 Qwen3.8-27B）：

| 项 | 实测结果 | 对设计的影响 |
|---|---|---|
| 最大上下文 | 8192 token（提问与回答合计） | 历史消息按预算截断；工具定义和工具返回的数据都必须精简 |
| 思考过程 | 默认开启，输出为"思考内容 + `</think>` + 正文"，没有起始标记 | 默认在请求里关闭思考；开启时由后端滤掉思考内容 |
| 关闭思考 | 请求里加 `chat_template_kwargs: {"enable_thinking": false}` 有效 | 由配置项 `LLM_ENABLE_THINKING` 控制 |
| 工具调用 | 流式和非流式都返回标准的 `tool_calls`，结束原因为 `tool_calls`；流式时参数分多段到达 | 按 OpenAI 标准格式解析，分段拼接参数 |

服务器上的程序版本：PostgreSQL 13、Redis 6.2、Nginx 1.24，均复用服务器已有程序并启动项目专用实例。
