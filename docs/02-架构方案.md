# 架构方案

更新日期：2026-11-16

## 技术选型

选型标准：好维护、资料多、有同类案例。

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | AkShare 是 Python 库；原生支持异步和流式输出；TradingAgents-CN、daily_stock_analysis 同栈 |
| 前端 | Vue 3 + TypeScript | 国内资料最多；TradingAgents-CN 同栈 |
| 图表 | ECharts | 一个库覆盖 K 线和财务图表，中文文档全 |
| 数据库 | PostgreSQL | 用户和会话是关系型数据；自带全文搜索 |
| 缓存与排队 | Redis | 行情缓存、模型并发排队 |
| PDF 导出 | 服务端无头浏览器渲染 | 图表和表格原样进入 PDF |
| 部署 | systemd + Nginx，不使用 Docker | 服务器上已有 PostgreSQL、Redis、Nginx 程序，直接启动项目专用实例 |

## 组成

```
浏览器（Vue 3 + ECharts）
   │  HTTPS；回答走流式连接
Nginx
   │
FastAPI 后端
   ├─ 账号：注册、登录、鉴权
   ├─ 对话：接收问题 → 排队 → 调模型 → 执行工具 → 流式返回
   ├─ 工具：行情、K 线、财报、选股、新闻（封装 AkShare）
   ├─ 会话：保存、搜索、重命名、删除、到期清理
   └─ 导出：会话 → PDF
   │
   ├─ PostgreSQL（用户、会话、消息）
   ├─ Redis（行情缓存、排队计数）
   ├─ 自研模型 API（外部）
   └─ AkShare → 公开数据网站（外部）
```

## 一次提问的流程

1. 前端发送问题，后端立即回一条状态消息（"已收到"或"排队中，前面 N 人"）。
2. 后端在并发名额内调用模型 API，带上工具定义和会话上文。
3. 模型请求调用工具时，后端执行对应的 AkShare 封装，前端显示"正在查询行情"等状态。
4. 工具结果返回模型，模型流式输出正文；图表和表格以结构化数据块随流下发，前端用 ECharts 渲染。
5. 回答结束后，问题、回答、图表数据、来源链接一并写入数据库。

## 关键设计与对应的验收项

| 设计 | 说明 | 对应验收 |
|---|---|---|
| 收到即回状态 | 不等模型，后端先推一条状态消息 | B1 |
| 并发闸门 | Redis 计数，同时最多 200 个模型请求，超出排队并推送排队位置 | B10 |
| 行情短缓存 | 同一只股票的行情缓存数秒，避免 300 人重复抓取被上游限流；缓存时长须小于 5 秒 | B3、B11 |
| 选股走本地库 | 定时把全市场行情和财务指标落到 PostgreSQL，选股条件转成查询，不临时抓全市场 | B7 |
| 工具失败不中断 | 工具出错时把"未获取"作为结果交还模型，由模型标注后继续作答 | B9 |
| 图表存数据不存图 | 消息里保存图表的原始数据，重开会话和导出 PDF 时重新渲染，即生成时的快照 | B4、C1、C5 |
| 按用户过滤 | 所有会话查询都带当前用户条件，在数据访问层统一加 | A3 |
| 到期清理 | 最后对话时间超过 30 天（`CONVERSATION_KEEP_DAYS`）的会话：查询时一律当作不存在，后台每小时实际删除一次。重命名不改最后对话时间 | C6 |
| 历史搜索 | 数据库 `ILIKE` 匹配标题和消息正文，不区分大小写；`%`、`_` 按字面匹配。数据量小，暂不建全文索引 | C2 |
| 删除会话 | 先删消息再删会话，不依赖数据库级联；回答生成中被删除的会话不再保存回答 | C4 |

## 数据工具（已实现部分）

模型通过工具调用取数，一次回答最多调用 4 轮工具。工具返回两样东西：给模型读的精简文字摘要，和直接交给页面展示的图表数据（不经过模型，不占上下文）。

| 工具 | 作用 | 数据来源 | 缓存 |
|---|---|---|---|
| `get_stock_quote` | 最新价、涨跌幅、今开、最高、最低、昨收、成交量、成交额 | 腾讯财经实时报价；不可用时换新浪财经实时报价；都不可用时退到新浪 1 分钟线 | 1 秒 |
| `get_kline` | 1/5/15/30/60 分钟、日、周、月 K 线，页面画图，模型拿摘要 | 新浪财经（经 AkShare） | 分钟线 20 秒，日线以上 5 分钟 |

| `get_financials` | 最近 2–8 个报告期的主要财务指标，页面显示表格，模型做解读。交给模型的是逐项文字而不是表格，并由程序写明盈亏、同比增减、营收与利润同比的方向关系和最近三期同比走向 | 新浪财经财务摘要（经 AkShare） | 1 小时 |
| `get_stock_news` | 一只股票最近的新闻，含原文链接 | 东方财富个股新闻（经 AkShare） | 2 分钟 |
| `get_market_news` | 财经媒体的最新市场资讯，可按关键词筛选，含原文链接 | 东方财富财经资讯，最近 200 条（经 AkShare） | 1 分钟 |
| `screen_stocks` | 条件选股：估值、行情、技术、财务、行业概念五类条件任意组合，结果以表格展示 | 见下方"条件选股" | 实时部分 60 秒 |
| `get_market_overview` | 大盘概况：主要指数、涨跌家数与分布、三市成交额、成交额前五、行业领涨领跌与资金流向 | 市场概览的快照（见下） | 随快照 |
| `get_policy` | 官方最新发布的政策文件和通告：标题、日期、官网原文链接，可按机构和标题关键词筛选 | 国务院、证监会、中国人民银行、财政部、国家发展改革委官网的发布列表（直接抓取） | 10 分钟 |

- 股票可用 6 位代码或简称指定。名称表随代码发布一份快照（`backend/app/tools/data/stocks.csv`），后端在后台每 12 小时从交易所刷新；刷新失败就继续用现有的，不影响查询。
- 没有使用东方财富的行情接口：实测其服务器对请求限流，首次请求即被拒绝，不适合 300 人使用。
- 实时报价直接请求腾讯、新浪的公开报价接口（AkShare 没有封装单只股票的实时报价，这是用户同意的例外）。实测腾讯报价滞后 1–5 秒，对应验收 B3。
- 日线以上用前复权数据；分钟线用不复权数据，因为复权后的分钟线不含当天。
- 缓存目前在后端进程内存里，没有用 Redis（后端是单进程）。
- 每个工具在结果末尾给出写好的来源链接，要求模型原样引用；模型采样温度设为 0.3 以减少漏调工具和改写数据。
- 官方政策原文直接抓取五家官网的发布列表（AkShare 没有对应接口，这是用户要求的）。每家一个解析函数，写在 `backend/app/tools/policy.py` 的 `SOURCES` 里；某一家改版或不可达时只影响那一家，并在回答里如实说明。只取标题、日期和链接，不取正文，模型不得臆测条款内容。要增加机构，在 `SOURCES` 里加一行。
- 登录后的首页是"市场概览"，对话在"智能投研"（`/chat`、`/c/<会话 id>`）。概览页和对话页右侧的看板共用一份市场快照 `GET /api/market/board`，不经过模型。后台任务定时刷新这份全站共用的快照，接口直接返回：页面从不等待上游，对每个上游的请求频率固定，与在线人数无关；两分钟没人看页面就停止刷新。各板块独立，某个数据源取不到时那一块不显示。
  - 9 个指数（上证、深证、创业板、沪深 300、科创 50、上证 50、中证 500、中证 1000、北证 50）与当天分时：腾讯财经，5 秒 / 60 秒。
  - 全市场统计（涨跌家数、涨停跌停、涨跌分布、涨幅榜、跌幅榜、成交额榜、三市成交额）：腾讯报价对沪深京全部股票逐只统计，约 19 次批量请求、不到 1 秒，30 秒一次；涨跌家数在腾讯不可用时退到乐咕乐股。
  - 行业板块（约 90 个行业的涨跌幅、资金净流入、领涨股，用于热力图和资金流向）：同花顺（经 AkShare），2 分钟。
  - 财经快讯：东方财富（经 AkShare），1 分钟；官方政策复用 `get_policy` 的数据，10 分钟。
  - 代码在 `backend/app/overview.py`。
- 指数详情 `GET /api/market/index/<代码>`：当日分时和最近 120 个交易日日 K（腾讯财经），同一指数 15 秒内只取一次。腾讯没有北证 50 的历史日线，该指数只显示分时。
- 登录页的指数行情 `GET /api/market/ticker` 不需要登录，只返回 5 个指数的公开点位。
- 模型工具 `get_market_overview` 把同一份快照整理成文字，供市场复盘和指数解读使用；没人看页面、快照已停时会先现取一次。
- 行情查询除文字外还返回一张行情卡片（`quote` 类型的展示块），价格数字由页面直接展示，不经模型转述。

## 条件选股（B7）

模型只把用户的话翻译成结构化条件（字段、比较符、数值），筛选由程序完成，股票名单只能来自工具结果。

| 数据 | 字段 | 来源 | 更新 |
|---|---|---|---|
| 实时 | 最新价、涨跌幅、市盈率 TTM、市净率、总市值、流通市值、换手率、量比、成交额、主力净流入、5/20/60 日与年初至今、52 周涨跌幅 | 腾讯排行接口（全市场约 28 次请求） | 选股时现取，60 秒内复用 |
| 实时 | 股息率、52 周最高（推出"距 52 周高点""创 52 周新高"） | 腾讯批量报价（约 19 次请求） | 同上 |
| 财务 | 最新报告期 ROE、营收同比、净利润同比、毛利率、每股收益、每股净资产、资产负债率；最新年报 ROE、近三年年报 ROE 最低值；所处行业 | 东方财富业绩报表、资产负债表（经 AkShare，约 5 次请求、40 秒） | 每天一次，存库 |
| 技术 | 均线多头排列、站上 20/60 日线、近 3 日 MACD 金叉、RSI14 | 由每只股票最近 130 根前复权日 K 计算（腾讯，约 5600 次请求） | 每个交易日 15:10 后一次，存库 |
| 概念 | 807 个概念板块及成分股 | 腾讯概念板块 | 板块列表 12 小时，成分股 6 小时，用到才取 |

- 数据快照存在 `screen_data` 表（迁移 0003），服务重启后直接读取，不必重新抓取。筛选在内存中用 pandas 完成（全市场约 5600 行）。这与最初"选股条件转成数据库查询"的设想不同：数据量小，内存筛选更简单，结果相同。
- 技术指标的抓取必须限速：实测连续两轮不限速的全市场请求后，腾讯防火墙封禁了日 K 接口（返回 501 网页）。现在 4 个并发、每次请求后歇 0.15 秒，全市场约 5.5 分钟；并在三个等价的日 K 地址之间自动切换，被封的地址 30 分钟内不再使用。
- 价格与均线的比较用最新价，均线本身截至上一个收盘（收盘后更新时即当天）；表格下方注明各部分数据的时间。
- 默认排除停牌、当天无成交和 ST 股票。没指定排序时按第一个数值条件排：要求"低于"的从低到高，要求"高于"的从高到低。
- 行业用东方财富的行业分类（约 150 家北交所新股暂无行业）；概念用腾讯的概念板块，成分股的划分以腾讯为准，个别归类可能宽泛。
- 不支持的条件（如 PEG、北向持股、机构评级）由工具报错，提示词要求模型如实告诉用户，不得换成别的指标。

**本地验证（2026-11-19）**：五类条件各跑一次，抽查结果用独立来源复核，全部满足——估值用腾讯单只报价接口核对市盈率、市净率、股息率；财务用新浪财务摘要核对 2023–2025 年报 ROE；行情用新浪日 K 核对 20 日涨幅和成交额；技术用新浪日 K 独立计算均线、MACD、RSI；行业与概念为成分筛选，叠加的财务条件同上。

## 火眼金睛

找出"开盘前或开盘时发生重大利好、且市场认可"的股票。规则写在 `backend/app/hawkeye.py`，由程序执行，不用模型判断。

- 公告来源：东方财富公告列表（按日期取全部公告，带公告类型和原文链接）和业绩预告（经 AkShare）。时间窗：上一交易日到今天披露的公告；收盘后和休市时改为"下一交易日预览"。交易日由上证指数日 K 判断，自动避开节假日。
- 利好强度：业绩预增（增幅 ≥ 50%）或扭亏 25~40；重大合同 / 中标 20；重组 / 收购控制权 20；新药或器械获批上市 18；控股股东增持计划 15；回购方案 12；临床试验获批 8；股权激励草案 8。律师意见、进展、修订稿等后续文件不重复计分。
- 盘面确认（只在盘中）：高开 1%~7% +15，高开超过 7% +8，低开 −10；量比 ≥ 5 +15，≥ 2 +10；开盘后继续走高 +5，较开盘回落超过 2% −8。
- 风险扣分：同期有减持、立案、处罚、预亏等公告 −25；开盘一字涨停未打开 −10；总市值小于 30 亿 −5；ST 不入选。
- 结果 60 秒内复用。每个交易日 9:35 后第一次计算的三星及以上名单定格存入 `screen_data`（名称 `hawkeye:日期`），页面上的"历史表现"统计这些股票从入选当天开盘价到现在的涨跌和上涨占比，用来检验规则。

## 个股详情与诊股（N1）

接口在 `backend/app/stock.py`，页面为 `/stock/代码`。任何出现股票名称的地方（排行榜、火眼金睛、自选股、选股结果表、对话里的行情卡片）都可点进详情；顶栏有股票搜索框。

- 详情：行情与估值（腾讯批量报价）、当日分时（腾讯）、最近 250 个交易日前复权日 K（腾讯）、8 期财务指标（新浪，与对话里的财务工具同源）、公告（东方财富公告接口）、新闻（东方财富）。各部分分开请求，某一部分取不到只影响那一块。
- 诊股：五项各 0–100 分，从 50 分起按规则加减，综合分为有数据各项的平均。每一条加减分都列出原因。
  - 基本面（东方财富业绩报表，即选股用的财务快照）：最新年报 ROE、净利润同比、营收同比、毛利率、资产负债率（银行、保险、证券不看负债率）。
  - 估值：市盈率 TTM 与同行业（东方财富行业分类，至少 5 家正市盈率）中位数比较，没有同行数据时按绝对水平；市净率；股息率。分数越高表示越便宜。
  - 技术面（日 K 自算）：均线排列、是否站上 20 / 60 日线、MACD 金叉死叉、RSI14 超买超卖、距一年最高价的位置。
  - 资金面：最近 5 个交易日主力净流入（东方财富资金流向，主力 = 超大单 + 大单；盘中用实时接口补上当天）；量比配合涨跌；换手率过高扣分。
  - 消息面：近 30 天公告标题，按火眼金睛的同一套规则识别利好和风险，另加业绩预增、扭亏。不看媒体新闻。
- 对话里新增工具 `diagnose_stock`：返回同样的评分和依据，页面在回答上方展示评分卡；提示词要求模型照抄分数、不给买卖建议。结果 60 秒内复用。

## 自选股与异动提醒（N2）

`backend/app/watchlist.py`，表 `watch_items`、`alerts`（迁移 0004）。每人最多 100 只。

- 后台任务每 30 秒一轮：交易时段（按交易日历判断）查自选股行情，涨跌幅达到该股阈值、触及涨跌停时提醒；每 5 分钟查一次自选股公告，只提醒加入自选之后、一天以内发布的（例行的每日股份变动报表不提醒），并按火眼金睛规则标注"利好类""风险类"；交易日 9:36 后若当天火眼金睛名单已定格，自选股在名单里的提醒一次。
- 去重键为"代码 + 事件 + 日期"（公告为公告编号），同一事件只提醒一次。提醒保留 30 天。
- 这个后台任务每个交易日 9:36 后会调用一次火眼金睛的计算，所以即使当天没人打开火眼金睛页面，名单也会定格存库，历史表现可以连续积累。
- 页面：顶栏铃铛每 30 秒查一次，有新提醒时右上角弹出；自选股页可改阈值。

## 每日报告（N3）

`backend/app/reports.py`，表 `daily_reports`（迁移 0004）。交易日历来自新浪（经 AkShare，含全年休市安排），取不到时按工作日判断。

- 早报：交易日 8:45 起生成（服务在盘中重启也会补一份，收盘后不再补）。数据：隔夜美股三大指数、中概股、港股、黄金、原油、美元人民币（腾讯）；上一交易日 A 股收盘概况（与 `get_market_overview` 同一份）；上一交易日 15:00 以来的财经新闻 15 条；近两日官方政策；火眼金睛三星及以上候选。
- 收盘复盘：交易日 15:30 起生成。数据：当日收盘概况、涨跌幅榜、当日新闻、当日政策、火眼金睛入选股当日表现。
- 程序先取齐数据整理成文字，再交给模型按固定结构写成报告；数据原文随报告存库，页面可展开核对。失败 10 分钟后重试，每类每天最多 3 次。
- 服务器上可手动生成：`python -m app.reports close`（已有则跳过），加 `--force` 重新生成并覆盖。

## 回答的流式显示

- 后端推来的文字片段每秒几十段，前端攒到下一帧再更新页面（每帧最多一次）。
- 生成中的回答按空行分段渲染，已完成的段落 HTML 不变，只有最后一段重绘；生成结束后整篇渲染一次。以前每来一段文字就重新渲染页面上所有回答。
- 跟随滚动：用户只要往上翻就停止自动滚到底部，滚回底部后恢复。以前按"离底部不到 120 像素就跟随"判断，滚轮上翻一格不到 120 像素，下一帧又被拉回底部，表现为闪屏。
- 模型偶尔把工具调用写成正文里的 `<tool_call>…</tool_call>` 文字。这段文字不再显示；能解析的，按正常工具调用执行。

## 上下文预算

每次请求都带上系统提示词和全部工具定义（约 2700 token）。模型服务每个副本的上下文上限为 32768（2026-11-19 用户核对实际运行的 vLLM 进程）；扣除回答预留 2000、工具结果预留 2500 后，历史对话可用约 25000 token。`LLM_CONTEXT_TOKENS` 不能大于模型服务的 `max_model_len`，`/api/health` 会显示两者并核对。

## 数据库迁移

表结构变更用 Alembic 管理，迁移文件在 `backend/migrations/versions/`，后端启动时自动执行到最新。改动 `app/models.py` 里的表结构后必须新增一个迁移文件。

## 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| AkShare 抓取公开网站，无服务保障，上游改版或限流会失效 | B3–B8 | 短缓存降低请求量；工具失败按 B9 处理；工具层做成可替换，日后可换商业数据源 |
| 5 秒延迟在上游变慢时可能超标 | B3 | 回答中始终标注数据时间；上线前在交易时段实测 |
| 东方财富资金流向、公告接口为网页接口，可能变更或限流 | N1、N2 | 取不到时诊股的资金面只按量价判断、消息面显示暂无数据；提醒下一轮重试 |
| 部分 AkShare 接口（新浪交易日历、新浪日 K、同花顺行业板块）在进程内用内嵌 V8 执行 JavaScript，多线程同时调用会让后端进程段错误退出 | 整体 | 这些接口一律经 `app/jsengine.py` 的同一把锁串行调用（等待超过 90 秒放弃）；新接入的 AkShare 接口先查是否用到 `py_mini_racer`，用到就同样包一层 |
| 注册不设限，网址外泄后外部人员可使用 | 整体 | 首版已确认不处理；可通过只在内网开放来规避 |

## 模型服务与服务器

| 项 | 内容 |
|---|---|
| 协议 | OpenAI 兼容 HTTP API |
| 地址 | 内网地址，不写入仓库，部署时在 `.env` 的 `LLM_BASE_URL` 中填写；对话接口为 `/v1/chat/completions` |
| 密钥 | 存于服务器上的文件，路径不写入仓库，部署时在 `.env` 的 `LLM_API_KEY_FILE` 中填写；后端进程的专用账户对该文件只有读权限 |
| 工具调用 | 请求中用 `tools` 声明，可设 `"tool_choice": "auto"` |
| 服务器 | Linux，可访问外网 |

实测到的模型行为（模型名 Qwen3.8-27B）：

| 项 | 实测结果 | 对设计的影响 |
|---|---|---|
| 最大上下文 | 32768 token（提问与回答合计）。早期测得 8192，2026-11-19 用户核对实际运行的进程为 32768 | 历史消息按预算截断；工具定义和工具返回的数据仍要精简 |
| 部署 | GPU 0–7 各运行一个 Qwen3.8-27B 副本（每副本单卡），对外一个地址 | 单个回答的出字速度取决于单卡；多人并发由多个副本分担 |
| 思考过程 | 默认开启，输出为"思考内容 + `</think>` + 正文"，没有起始标记 | 默认在请求里关闭思考；开启时由后端滤掉思考内容 |
| 关闭思考 | 请求里加 `chat_template_kwargs: {"enable_thinking": false}` 有效 | 由配置项 `LLM_ENABLE_THINKING` 控制 |
| 工具调用 | 流式和非流式都返回标准的 `tool_calls`，结束原因为 `tool_calls`；流式时参数分多段到达 | 按 OpenAI 标准格式解析，分段拼接参数 |

服务器上的程序版本：PostgreSQL 13、Redis 6.2、Nginx 1.24，均复用服务器已有程序并启动项目专用实例。
